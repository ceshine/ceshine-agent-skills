# Operation 3: Generate Commit Message for Staged Changes

Draft a conventional commit message for staged changes and commit them after user approval. `<repo-root>` is the absolute path to the target repository.

1. **Collect staged changes** - Run `scripts/git-cached-diff.sh <repo-root>`. If the output is empty, tell the user there is nothing staged and stop.
2. **Review (optional)** - Skip this step unless the user or the invoking skill requests a review. When requested:
   - Review the staged changes with `references/op_review.md`: read the guidelines it lists first, then do "1a. Review Staged Changes" (the diff from step 1 can be reused). Do this unless the requester specifies another method (e.g., delegating to a subagent).
   - Present the findings and wait for feedback. The user may:
     - Edit the staged changes
     - Acknowledge issues if any but proceed
     - Ask for clarification
     - Or simply confirm they have reviewed the findings and approve moving on

     **Only move on to the next step after an explicit approval from the user.** If the staged changes were edited, run step 1 again before drafting.
3. **Load history** - Load the three most recent commit messages (e.g., `scripts/git-commit-messages.sh <repo-root> HEAD~3`) to ensure historical context.
4. **Draft the commit message** - Write it to `{cwd}/cache/commit_message.txt` in the conventional commit format (`{cwd}` is the directory in which the agent was invoked; first remove the file if it already exists, then write to it):
   ```
   <type>(<scope>): <subject>

   <body>

   Commit message generated by <your name>
   ```
   - Type: feat, fix, docs, style, refactor, test, chore
   - Scope: (optional) the area of code affected
   - Description: brief explanation of changes
   - Body: itemized details of changes. Highlight breaking changes or issue references
   - Footer: Ask the user what your name is if uncertain. It should be in the format: `<harness name> (<model name>)` (e.g., `Claude Code (Sonnet 4.6)`)
5. **Display the commit message** - The user may:
   - Request revision
   - Approve the commit message -> Commit the changes with the message and end the process.
